## Three Different Records

The three append-only histories deliberately answer different questions:

| Record | Question | Source of truth for |
| --- | --- | --- |
| State Event | What lifecycle state is the Run in? | Run, Stage, Approval, ProviderAction |
| Execution Event | How was one daemon invocation scheduled? | enqueue, lease, retry, cancellation, recovery |
| Evidence | What proves the delivered result? | artifacts, tests, review, delivery |

A heartbeat is mutable liveness data on an execution job. It is not appended
every five seconds because it would add noise without improving the audit
story. Lease acquisition, loss, recovery, cancellation, and reconciliation are
immutable Execution Events.

## Persistence And Transactions

Blackboard schema v3 adds:

- `run_specs`, containing a versioned and hashed credential-free RunSpec;
- `execution_jobs`, one row for each start or resume invocation;
- `execution_events`, ordered per Run with idempotency keys;
- `daemon_instances`, containing local process and heartbeat diagnostics.

Run creation, RunSpec persistence, initial Job creation, and
`execution.enqueued` commit in one `BEGIN IMMEDIATE` transaction. A partial
submission is therefore neither visible nor claimable. The partial unique index
over active Job states prevents two active invocations for one Run.

Claiming is FIFO by `available_at_ms`, then creation time. Each claim creates a
random lease token and increments a numeric fencing token. Heartbeat, completion,
retry, and cancellation acknowledgement require all lease fields to match.

## Execution Guard

Every Blackboard used by a daemon Runtime has an Execution Guard. Immediately
before an outer SQLite transaction commits, the Guard verifies:

1. the cooperative token is not cancelled and has not lost its lease;
2. the Job still belongs to this Daemon/Worker and lease token;
3. the fencing token is current;
4. the lease has not expired and the Job remains leased or running.

This check covers direct Blackboard CRUD as well as LifecycleService writes. A
stale Worker can continue executing Python briefly, but it cannot declare a
Stage, Evidence bundle, artifact, or Run completion committed.

## Worker And Retry Contract

The local pool defaults to two Workers. Configuration lives under `[daemon]`:

```toml
[daemon]
workers = 2
lease_seconds = 30
heartbeat_seconds = 5
cancel_grace_seconds = 10
```

Infrastructure failures retry at 1, 5, and 30 seconds, up to three claims.
Provider/test/review outcomes remain domain results and are not blindly replayed
by the scheduler. A clean pause for an approval, feedback, budget, or Provider
action makes the current Job `succeeded`; the Run retains its waiting status.

Local scheduling is at-least-once. muxdev does not claim exactly-once effects
for opaque Provider CLIs.

## Cancellation

Queued jobs cancel immediately. A running cancellation is first persisted as
`cancel_requested`; Runtime checks the token at Stage boundaries and the
headless subprocess backend checks it while streaming output. The backend asks
the controlled process to exit, waits the configured grace interval, and then
terminates that exact process tree. Only acknowledgement changes the Job to
`cancelled` and the Run to `aborted`.

`muxdev task stop` and the old root `muxdev stop` remain aliases. New automation
should use `muxdev task cancel` so requested and acknowledged states are not
confused.

## Restart Reconciliation

| Observation after lease expiry | Decision |
| --- | --- |
| No running Provider attempt | Return to `retry_wait` and resume from durable Stage state |
| Persistent cancellation request | Confirm cancelled and abort the Run |
| Opaque Provider attempt still running | Enter `reconciliation_required` |
| Legacy running Run with missing worktree | Enter `reconciliation_required` |
| Completed or intentionally waiting Run | Do not enqueue another Job |

The Worker Pool rechecks expired leases while idle, so a Daemon that restarts
before the old 30-second lease expires recovers when the lease actually becomes
stale. It never kills an old PID whose identity cannot be proven.

An ambiguous Job requires `retry` or `abort`. Retry requires a reason and an
explicit acknowledgement that an external Provider effect may be duplicated.
Both choices append an Execution Event.

## Management Surface

```text
muxdev task cancel RUN_ID [--reason TEXT] [--wait]
muxdev task executions RUN_ID
muxdev task reconcile RUN_ID --retry|--abort --reason TEXT --yes
muxdev runtime status
```

The local HTTP equivalents are `/api/tasks/{run_id}/cancel`,
`/api/tasks/{run_id}/executions`, `/api/tasks/{run_id}/reconcile`, and
`/api/runtime/status`. Mutations enforce loopback Origin policy. Responses omit
lease tokens, fencing tokens, full RunSpecs, environment variables, prompts,
and process arguments. WebSocket `execution_event@1` is emitted only after the
transaction commits; heartbeats are not broadcast.
