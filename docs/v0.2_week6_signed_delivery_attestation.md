# muxdev v0.2 Week 6: Signed Delivery Attestation And Offline Trust

## Status

**当前已实现:** Blackboard schema v6, RunSpec v4, per-project Ed25519
identities, atomic signed completion, privacy-minimal `.muxattest` export, and
pure offline verification are on the main path. Every new completed Run attempts
an attestation. A high-risk Run fails closed; an ordinary Run may complete with
an explicit `unsigned` record and cannot contribute a production routing
outcome.

**后续状态:** Week 7 now projects this proof through TaskStory and the task-first
Dashboard. Week 8 adds deterministic Replay, authenticated local APIs and RC
build artifacts. Real Provider Benchmark measurement and external publishing
remain explicit operator actions. muxdev does not add a remote CA, transparency
log, HSM, Sigstore identity, or Provider exactly-once guarantee.

## Product Meaning

DeliveryAttestation answers a narrower and more defensible question than “did
the model do a good job?” It proves that a particular muxdev project identity
signed a canonical statement binding the Run, repository baseline, route,
Adapter certification, isolation, review, approvals, tests, Evidence, event
heads, and allowlisted deliverables.

A valid self-contained signature proves integrity. It does not establish a
company, employee, CI system, or legal identity. Without an independently
pinned fingerprint, verification reports `self_asserted`. With the correct
fingerprint it reports `trusted`; a different fingerprint is `mismatch` and
fails verification.

## DeliveryAttestation v1

The payload contract is `muxdev.delivery-attestation.v1`. Serialization uses
`muxdev.canonical-json.v1`:

- UTF-8 encoding and Unicode NFC normalization;
- lexicographically sorted object keys and compact separators;
- JSON string keys only;
- rejection of NaN, Infinity, byte strings, and non-JSON values.

The payload binds:

- Run ID, task SHA-256, RunSpec version/hash/history status, workflow, risk,
  delivery mode, simulation flag, generation, and previous attestation hash;
- stable project UUID, start/end Git commits, initial dirty/untracked hashes,
  and final patch hash;
- RouteDecision/feature/policy/scorer/benchmark identifiers and hashes;
- selected main Agent, Reviewer, frozen review snapshot, verdict, and waiver;
- typed Approval ID/type/status/subject hash/decision time/operator source;
- Provider Attempt terminal projections, Adapter/certification/trust/isolation,
  exit code, waiver, and Harness Event chain heads;
- command/result hashes for test projections, never the raw command;
- Evidence events/manifest/evaluation hashes and chain head;
- the uncommitted completed State Event hash and derived Execution Event head at
  signing time;
- OS, architecture, Python, muxdev, Git, Provider/Adapter, and policy versions,
  excluding hostname, username, absolute paths, and environment values;
- allowlisted relative artifact path, size, media type, and SHA-256;
- attestation/key identifiers, signer fingerprint, target state, and signing
  time.

The detached signature envelope is `muxdev.ed25519-signature.v1`. It contains
the Ed25519 signature, payload hash, DER SubjectPublicKeyInfo public key, key ID,
project ID, and public-key fingerprint. The private key is never embedded.

Verification has independent outputs:

```text
integrity_valid
evidence_valid
identity_status: trusted | self_asserted | mismatch | unsigned
trusted
valid
warnings
errors
```

## Per-Project Identity And Key Governance

`.muxdev/trust/project-id` stores a non-secret UUID. Moving a project retains
its identity; a normal clone starts a new identity because `.muxdev` is ignored.
Public identity metadata and rotation records live under `.muxdev/trust`.

Private PKCS#8 keys live only under:

```text
MUXDEV_HOME/data/signing/projects/{project_id}/{key_id}.key.pem
```

They are physically separate from Provider state. POSIX uses `0700/0600`.
Windows attempts a current-user-only ACL and reports `permission_degraded` when
that cannot be proven. Permission degradation prevents high-risk signing.

The first signing attempt atomically creates an identity. If public identity
exists but the current private key is missing, muxdev refuses silent
replacement. `trust rotate` creates a record signed by both old and new keys,
persists both public keys, selects the new identity, then destroys the old
private key. Old bundles remain verifiable because they carry their public key.

CLI:

```text
muxdev trust status [--json]
muxdev trust init [--json]
muxdev trust rotate --reason TEXT --yes [--json]
muxdev trust public-key [--output PATH] [--json]
```

HTTP exposes only the public status summary. It has no key creation, rotation,
private import/export, arbitrary signing, or raw payload endpoint.

## Atomic Completion

`attesting` is a non-terminal Run state. The completion sequence is:

1. publish delivery artifacts, reviewer result, Evidence, and local report;
2. enter `attesting` and prepare a privacy-minimal signed report;
3. open one `BEGIN IMMEDIATE` transaction;
4. append the `run.transitioned -> completed` State Event;
5. build/sign the payload using that uncommitted event hash;
6. insert the immutable attestation generation and update the Run projection;
7. commit both together;
8. broadcast `attestation_created@1` and materialize cache files only after
   commit.

The database is authoritative. Missing `attestation.json`, `signature.json`, or
public PEM files can be rebuilt from it. A failure injected between the event
and attestation insert rolls back both.

High-risk signing, permission, Approval, or Evidence failure returns the Run to
`blocked` with `attestation_required`. An ordinary signing failure commits an
`unsigned` record and a persistent warning. Mock and Replay attestations set
`simulation=true`; they are not production delivery evidence. A repaired
completed Run creates a new immutable generation linked to the prior payload
hash.

Only a signed, Evidence-valid production generation may create a production
`routing_outcomes` sample. This prevents an unsigned compatible completion from
training the quality router.

## Approval And Evidence Boundary

New approvals always carry a versioned subject. The attestation preflight
recomputes its canonical hash. High-risk signing rejects a missing/untyped
subject, drift, a non-approved decision, or an invalid waiver. Approval records
also support `operator_source` and `decision_reason`; only the non-sensitive
operator source is projected into the attestation.

Evidence ArtifactRef now supports `scope + relative_path`. New Run-owned
references contain no absolute path. Local verification still accepts legacy
absolute records. Legacy completed Runs are displayed as
`legacy_unsigned/history_incomplete`; muxdev does not retroactively convert old
local metadata into trusted proof.

The fact boundaries remain:

| Fact | Responsibility |
| --- | --- |
| Run State Event | business lifecycle and the completed anchor |
| Execution Event | queue, lease, cancellation, recovery; head at signing time |
| Harness Event | structured facts inside one Provider Attempt |
| Evidence v2 | delivery claims, artifact references, and evaluation |
| DeliveryAttestation | signed binding of selected heads and deliverables |

## Offline Bundle And Interfaces

The bundle format and security rules are specified in
[`muxattest_format.md`](muxattest_format.md).

CLI:

```text
muxdev attestation show RUN_ID [--json]
muxdev attestation export RUN_ID --output FILE.muxattest [--json]
muxdev attestation verify RUN_ID|FILE.muxattest \
  [--trusted-fingerprint SHA256] [--require-trusted] [--json]
```

`muxdev evidence verify` now includes an attestation section. Ordinary unsigned
delivery keeps its Evidence result with a warning. Invalid high-risk signing or
`--require-trusted` failure produces an unsuccessful overall result.

HTTP:

```text
GET  /api/trust/status
GET  /api/tasks/{run_id}/attestation
POST /api/tasks/{run_id}/attestation-exports
POST /api/attestation-exports/{export_id}/verify
```

POST endpoints require the existing loopback Origin policy. They accept no
path, public-key path, fingerprint override, private key, raw payload, or extra
artifact list. Only a server-generated export ID can be verified.

## Demo

1. Run `muxdev trust status`, initialize if necessary, and pin the displayed
   fingerprint out of band.
2. Complete a Mock/Replay task and inspect its `simulation` attestation.
3. Export a `.muxattest` file and copy it to a clean directory without a
   database, Provider, or muxdev project.
4. Verify once without pinning (`self_asserted`) and once with the correct
   fingerprint (`trusted`).
5. Modify a bundle member or payload and show verification failure.
6. Rotate the key, verify the old bundle, and show a new Run using the new
   fingerprint.
7. Inject a missing/degraded key: an ordinary task finishes `unsigned`; a
   high-risk task remains `blocked`.

## Residual Risk

- A compromised host or private key can sign malicious later statements.
- Self-contained public keys provide integrity, not external identity.
- Attestation does not make Provider side effects exactly-once.
- The safe diff and selected reports may still contain source-sensitive data;
  the exporter never adds arbitrary files, but users must choose recipients.
- No remote revocation, transparency, timestamp authority, or organization
  policy exists in Week 6.
