# muxdev v0.2 Week 5: Capability-Constrained Routing And Heterogeneous Review

## Status

**当前已实现:** RunSpec v3 persists a task-level routing policy. Before any
Provider call, muxdev extracts bounded repository features, evaluates only
certified Adapter capabilities, records an immutable `RouteDecision`, and
projects the selected main Provider into the Run. High-risk tasks require a
different, certified, read-only Reviewer or a subject-bound human waiver.
Blackboard schema v5 stores task features, route decisions, verified outcomes,
review assignments, and registered benchmark snapshots.

**v0.2 目标:** Week 6 will bind the RouteDecision, review result, certification,
isolation, approvals, Harness Events, and delivered artifact hashes into a
signed DeliveryAttestation. The Week 5 benchmark command registers a bounded
offline or explicitly acknowledged live execution plan; it does not yet run a
paid multi-provider benchmark or publish quality claims.

## Product Contract

Routing is performed once per Task Unit. It chooses one main Agent and, when
risk requires it, one heterogeneous read-only Reviewer. It does not recreate a
fixed analyst/architect/coder/tester role pipeline and does not switch Providers
mid-run after an opaque failure.

The decision priority is:

1. availability and certification currency;
2. required verified capabilities and isolation;
3. production versus simulation delivery boundary;
4. Provider allowlist and total task budget;
5. conservative verified quality evidence;
6. deterministic cost, latency, and Provider-name tie breaks.

Only capabilities with status `verified` satisfy policy. Provider branding,
help text, an `advertised` capability, or a legacy score cannot make a candidate
eligible.

## Durable Contracts

### TaskFeatureSet

The extractor records bounded metadata rather than source content:

- task class and change-scope bucket;
- dominant languages and repository-size bucket;
- detected build and test systems;
- risk level/tags and required capabilities;
- certification, isolation, delivery-mode, and budget requirements;
- extractor version and a canonical source hash.

The persisted payload contains no task prompt, source text, file path, secret,
credential, or environment value. The extractor does not follow symlinks and
skips `.git`, `.muxdev`, virtual environments, dependency trees, caches, and
build output. It has a hard file-count bound.

### RouteDecision

`RouteDecision` version 1 binds:

```text
decision_id
run_id
idempotency_key
feature_set_id + feature_hash
candidate snapshots and exclusion codes
selected main and reviewer Providers
benchmark snapshot id + hash
policy and scorer versions
reason codes
previous/superseded decision references
decision_hash
```

Feature persistence, decision persistence, and the selected-Provider Run
projection use explicit transactions. Repeating the same idempotency key
returns the original decision. WebSocket `route_decision@1` is queued only
after commit. Resume reuses the stored decision; a replay is a side-effect-free
comparison and is always labelled simulation/non-production evidence.

### RoutingPolicySpec

RunSpec v3 adds:

```text
mode: auto | fixed | replay
delivery_mode: production | simulation
fixed_provider
allowed_providers
reviewer_policy: auto | required | disabled
minimum_samples
benchmark_snapshot_id
max_cost_usd
```

RunSpec v1/v2 imports use a conservative fixed-provider policy so an old task
cannot silently acquire a new Provider. An explicit fixed Provider is recorded
even when it needs an existing certification/isolation waiver, allowing the
Harness preflight to pause before launch rather than silently choosing another
Provider.

## Conservative Quality Routing

Only outcomes written after complete delivery evidence are eligible learning
samples. A sample is partitioned by task class and production/simulation
source. Incomplete evidence, a Replay result, or a Mock result cannot improve a
real Provider's production estimate.

For each candidate muxdev applies a Jeffreys-prior Beta posterior and records a
conservative lower bound, sample count, and observed p90 cost/latency. Sparse
data prefers the configured certified fallback. Once evidence is sufficient,
the main Agent is selected by lower-bound quality first, followed by sample
count, cost, latency, and a stable lexical tie break. The decision stores inputs
and versions, so it can be explained and reproduced without calling a model.

This is bounded statistical routing, not autonomous online learning. There is
no prompt embedding, cross-project source retention, opaque reward, Provider
name heuristic, or unreviewed self-modifying policy.

## Heterogeneous Read-Only Review

A Reviewer is required when `reviewer_policy=required`, or whenever the Harness
risk level is high. `reviewer_policy=disabled` can suppress review only for an
ordinary task; it cannot weaken a high-risk policy. A valid Reviewer must:

- be eligible under the same certification/isolation/delivery policy;
- be a different Provider from the main Agent;
- have a different executable/fixture fingerprint where both are known;
- have `read_only=verified`;
- keep main-plus-reviewer observed p90 cost inside the task budget.

The assignment is bound to the RouteDecision. Before the final review stage,
muxdev freezes a minimal snapshot containing the patch hash and size, hashed
test summaries, stage-contract references, and artifact hashes. It deliberately
omits the main Provider identity. The Reviewer receives a blind, read-only
instruction. Runtime verifies both the frozen snapshot hash and the worktree
patch hash after the attempt. A write attempt becomes a high-severity blocker.

Review output must satisfy the structured ReviewResult contract. High/critical
findings reject the assignment. One new bounded retry is allowed after a repair;
history is not overwritten. A Run with an assigned/running/blocked required
review cannot transition to `completed`.

Codex and Qwen remain opaque and currently do not have verified read-only
review capability, so they cannot be promoted to Reviewer merely because they
can inspect files. Managed Mock/Replay exercise this contract deterministically
for tests and demos.

### Reviewer-Unavailable Approval

When no valid heterogeneous Reviewer exists, muxdev pauses before the main
Provider call and creates `heterogeneous_review_unavailable`. Its subject binds
the Run, RouteDecision/hash, feature hash, main Provider, risk policy, and all
reviewer candidate exclusions. Approval creates an auditable `waived`
assignment; denial blocks the Run. A changed decision or policy changes the
subject hash, so an older waiver cannot be reused.

Isolation preflight runs before reviewer preflight. Therefore a high-risk
opaque Provider that lacks strong isolation still asks for
`isolation_downgrade` first and cannot hide that risk behind a reviewer waiver.

## Fact And Transaction Boundaries

| Fact | Responsibility |
| --- | --- |
| Run State Event | business lifecycle, including `routing` and `reviewing` |
| Execution Event | queue, lease, retry, cancellation, recovery |
| Harness Event | facts inside one Provider Attempt |
| RouteDecision / ReviewAssignment | immutable selection inputs and independent-review state |
| Evidence | delivered claims and verification material |

Routing outcomes are written only after reports, Evidence, artifacts, and
delivery records exist. They are not Evidence themselves. Heartbeats and model
message deltas do not enter routing facts.

## Storage And Interfaces

Blackboard migration v5 adds:

- `task_feature_sets`;
- `route_decisions`;
- `routing_outcomes`;
- `review_assignments`;
- `benchmark_snapshots`.

CLI:

```text
muxdev task route RUN_ID [--json]
muxdev task review RUN_ID [--json]
muxdev routing replay RUN_ID [--benchmark SNAPSHOT_ID] [--json]
muxdev routing snapshots [--json]
muxdev routing benchmark trusted-routing-v1 [--live --yes --max-cost-usd N] [--json]
```

HTTP:

```text
GET  /api/tasks/{run_id}/route
GET  /api/tasks/{run_id}/review
GET  /api/routing/snapshots
POST /api/routing/replays
POST /api/routing/benchmarks
```

HTTP accepts neither arbitrary candidate scores nor Provider commands, fixture
paths, executable paths, source payloads, or a force-route mutation. Mutating
replay/benchmark requests retain loopback Origin/auth enforcement.

## Benchmark Boundary

`benchmarks/trusted-routing/v1/manifest.yaml` registers 24 cases covering
bugfix, feature, refactor, test, documentation, and security/migration work.
Each case uses a repository fixture identifier and hidden-test identifier rather
than an arbitrary caller path.

The current command validates and stores a hash-bound plan for fixed Codex,
fixed Qwen, legacy rules, and the v0.2 router. `--live` requires `--yes` and a
positive total budget, but registering that plan does not execute Providers.
No README/resume quality improvement is claimed until the later release step
has executed the held-out suite and published reproducible results.
