# muxdev v0.2 Threat Model

Status: **v0.2 RC threat model**. Week 1–8 controls described as implemented are
on the current repository path; remaining targets and residual risks are kept
explicit rather than treating a local deployment as inherently trusted.

## Assets And Trust Boundaries

Protected assets are source code, Git history, provider credentials, task and
approval records, evidence artifacts, local memory, and the operator's machine.
The principal boundaries are:

- browser or CLI client to the loopback API;
- API request to a registered project root;
- daemon scheduler to a worker and agent harness process;
- agent harness to its filesystem, shell, network, and credentials;
- worktree output to the user's project and Git branch;
- recorded evidence to an offline verifier or human reviewer.

External provider CLIs and content read from a repository are untrusted inputs.
An `opaque` CLI may execute tools that muxdev cannot observe before execution.

## Threat Register

### Workspace escape and project confusion

Threats include `..` traversal, symlink/junction escape, a nested path resolving
to the wrong outer project, an arbitrary API `workspace`, and the global
`~/.muxdev` directory being mistaken for a project marker.

- Current safeguard: run artifacts and worktrees normally live under a resolved
  workspace and many changes are reviewable as Git diffs.
- Week-one control: canonicalize the requested directory, select the nearest
  valid project marker, ignore the user's global `.muxdev`, reject missing or
  non-directory workspaces, and test nested and escaping paths.
- v0.2 control: require explicit project registration and enforce a canonical
  allowlist for every file-bearing API and worker request.
- Residual risk: operating-system junction and case-folding behavior differs by
  platform and requires platform-specific tests.

### Local API abuse

A malicious webpage or local process may call state-changing loopback endpoints
to submit tasks, approve changes, expose transcripts, or request rollback.

- Current safeguard: production server startup refuses non-loopback binding and
  creates a daemon-private 256-bit bearer token. CLI/TUI read the private file;
  the browser exchanges a 60-second single-use nonce for an HttpOnly,
  SameSite=Strict cookie. All task-bearing API and WebSocket paths authenticate,
  mutations validate loopback Origin, request/event sizes are bounded, storage
  APIs accept only server-generated IDs, and HTTP exposes no restore/live
  Benchmark route.
- Implemented v0.2 control: random bearer and browser bootstrap authentication,
  restrictive token-file permissions, Origin checks, consistent middleware,
  path-free request schemas, token rotation, and sanitized diagnostics.
- Residual risk: another process running as the same OS user may still read
  local files; stronger separation requires OS accounts or a remote service.

### Opaque agent actions

An opaque provider CLI may run shell, network, or file operations internally
without emitting a pre-execution event. Post-run transcript parsing cannot
enforce an action-level policy.

- Current safeguard: separate worktrees, stage-level approvals, process output,
  diffs, and rollback snapshots.
- Week-one control: label generic CLI integrations as `opaque` and stop claiming
  action-level interception.
- v0.2 control: certified capability profiles, minimum environment, process-level
  cancellation, strict container mode for sensitive tasks, and managed adapters
  where protocols expose pauseable structured actions.
- Residual risk: worktree isolation alone is not a security sandbox. Sensitive
  opaque tasks require Docker or an explicit recorded downgrade.

### Credential and secret exposure

Provider configuration, auth tokens, repository secrets, prompts, transcripts,
and environment variables may be copied into a worktree or evidence bundle.

- Current safeguard: output redaction and isolated provider state are used in
  parts of the runtime.
- v0.2 control: stop copying complete credential directories; mount or broker
  only the required credential, pass an allowlisted environment, redact before
  persistence, and run secret scanning over artifacts and logs.
- Residual risk: a provider with network and credential access can exfiltrate a
  secret it can read; policy must minimize simultaneous access.

### Worktree and sandbox confusion

Git worktrees protect branch isolation but do not constrain filesystem paths,
processes, resources, or network. Copy fallbacks can also inherit unintended
files if exclusion rules drift.

- Current safeguard: a dedicated Git worktree or copy is created per run and
  runtime directories are excluded from copy fallbacks.
- v0.2 control: explicit trust mode in every run, minimal mounts and environment,
  CPU/memory/time limits, network-off defaults for strict mode, and cleanup/GC
  with path validation.
- Residual risk: cross-platform container availability varies; reduced-isolation
  local mode remains a declared trade-off.

### Evidence tampering, self-assertion, and replay

A hash chain proves internal consistency only while its trusted head remains
anchored. A malicious actor able to rewrite every local artifact can regenerate
an unsigned chain. Old approvals may also be replayed against changed content.

- Current safeguard: Evidence v2 hashes events and referenced artifacts. Week 6
  signs the completed State Event and selected facts using a per-project local
  Ed25519 key, commits proof and completion atomically, and exports only a
  bounded allowlist through a path-safe `.muxattest` bundle.
- Implemented v0.2 control: bind task,
  route, policy, patch, commands, tests, environment, and approval subject hashes;
  invalidate approvals after subject changes; support offline verification and
  optional out-of-band fingerprint pinning. A bundle-carried key remains
  `self_asserted`.
- Residual risk: compromise of the signing key or the host can forge evidence;
  team mode should support an external transparency or CI anchor.

### Scheduler duplication and stale workers

Daemon crashes, run-id collisions, background threads, retries, or timeouts can
produce duplicate provider calls or leave work running after cancellation.

- Current safeguard: the SQLite-backed execution queue allows one active Job per
  Run; atomic claims use random lease tokens and increasing fencing tokens. A
  bounded Worker Pool renews leases, persists cancellation, and validates the
  execution fence before Runtime database commits. Safe expired work is
  requeued, while unknown opaque Provider outcomes require explicit retry or
  abort reconciliation.
- Week-one control: collision-resistant run IDs, worker waiting and cleanup, and
  diagnostics for non-terminal tasks.
- v0.2 control: certify Provider-specific cancellation, add stronger process
  isolation, and bind execution history into signed delivery attestations.
- Residual risk: exactly-once external effects cannot be guaranteed when an
  external harness lacks idempotent operations; attestations must expose that.

### Operational state corruption and unsafe restore

A crash or concurrent writer may split related lifecycle records. A crafted
backup can contain traversal names, modified databases, unsupported schemas, or
stale WAL sidecars; restoring it through a live Daemon may corrupt state.

- Current safeguard: the core lifecycle appends ordered, hash-linked events and
  updates projections in one `BEGIN IMMEDIATE` transaction. SQLite uses
  WAL/FULL, foreign keys, checksummed migrations, integrity checks, and visible
  degradation. Backup verification rejects traversal, undeclared members,
  duplicate logical targets, hash mismatch, failed database integrity, and
  unsupported schema versions. Restore is CLI-only, requires a stopped Daemon
  and explicit confirmation, makes a pre-restore backup, handles sidecars, and
  rolls replacements back on failure.
- v0.2 control: anchor operational snapshots in signed delivery attestations
  and add restart reconciliation after the durable scheduler exists.
- Residual risk: an attacker with full write access to the host can rewrite a
  database and all unsigned local metadata. Week-two event hashes detect
  inconsistency, not a fully compromised host.

## Security Acceptance

- a home-level `.muxdev` never captures an unrelated child workspace;
- missing, file-valued, escaping, and unregistered workspace inputs are rejected;
- every adapter exposes a trust tier and certified capability set;
- secrets are absent from persisted sample transcripts and evidence fixtures;
- approval replay against a changed subject is rejected;
- corrupt or path-escaping storage archives are rejected and restore cannot run
  while the Daemon is live;
- any signed attestation mutation fails offline verification;
- an unsigned ordinary completion is visibly untrusted and cannot update
  production routing outcomes;
- ZIP Slip, drive paths, duplicates, symlinks, undeclared files, oversized
  members, and compression bombs are rejected without extraction;
- strict-mode tests cover mount, environment, resource, and network boundaries.
