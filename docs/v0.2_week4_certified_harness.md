# muxdev v0.2 Week 4: Certified Adapters And Tiered Isolation

## Status

**当前已实现:** Codex, Qwen, Mock, and Replay use a versioned Agent Harness
lifecycle. Capabilities are four-state certification results, Codex/Qwen have
provider-specific event decoders, Blackboard schema v4 stores certifications
and hash-chained Harness Events, RunSpec v2 persists risk/isolation policy, and
high-risk isolation shortfalls pause before Provider launch.

**后续状态:** Week 5 now uses these verified capabilities for constrained
routing and heterogeneous read-only review. Week 6 remains the target for
binding certification, isolation, approvals, RouteDecision, review, and Harness
Events into signed Delivery Attestations.

## Agent Harness Contract

Every certified Adapter implements contract version 1:

```text
probe()       -> AdapterProbe
certify()     -> CertificationReport
start()       -> AttemptHandle
events()      -> Iterator[HarnessEvent]
cancel()      -> CancelResult
resume()      -> AttemptHandle | Unsupported
```

The old `run_stage()` API remains available, but Mock, Replay, Codex, and Qwen
now implement it through this lifecycle. Generic CLI configuration remains an
experimental `uncertified + opaque` compatibility path.

The standard capability vocabulary is:

```text
structured_events  tool_events       usage
session_resume     cooperative_cancel approval_bridge
read_only          patch_output       provider_sandbox
```

Each value is `verified`, `advertised`, `unsupported`, or `unknown`. Only
`verified` satisfies execution policy. A help flag can produce `advertised`; it
cannot prove runtime semantics. Unknown or malformed Provider records are
stored as `provider.unknown` rather than being interpreted as tool calls or
approvals.

Certification does not set trust. Codex and Qwen remain `opaque` because their
headless streams do not expose a muxdev-controlled, pauseable action protocol.
Mock and Replay are `managed` because muxdev owns their complete deterministic
lifecycle.

## Certified Adapters

### Codex

The Codex Adapter invokes `codex exec --json` with `workspace-write`, no
interactive approval, controlled working directory, and stdin prompt
transport. Its decoder maps session, turn, item, tool, usage, terminal, error,
unknown, and malformed JSONL facts. An Attempt records Codex version, Adapter
version, certification id, trust tier, isolation mode, and waiver reference.

Crash-safe resume is not declared verified. An opaque in-flight Codex Attempt
still enters third-week reconciliation after a Daemon crash.

### Qwen

The Qwen Adapter uses bare mode, sandbox mode, automatic Provider approval,
Stream-JSON, and a 40-tool-call ceiling. It never selects `yolo`: Qwen's
[official headless documentation](https://qwenlm.github.io/qwen-code-docs/en/users/features/headless/)
states that `yolo` does not itself enable sandboxing. Resume, usage, terminal,
and cancellation capabilities are exposed only at their certified state.

### Mock And Replay

Mock emits deterministic tool, usage, cancellation, artifact, and terminal
facts. Replay accepts only an in-memory built-in fixture or a fixture under a
registered directory whose canonical JSON hash matches the registered hash. It
never invokes shell, network, or a Provider. Every replay artifact says
`SIMULATED REPLAY` and explicitly excludes itself from production delivery
evidence.

## Offline And Live Certification

Offline certification is the default and makes no model call. It performs:

1. executable/version/help discovery with a minimal environment;
2. Adapter command and provider-specific JSON fixture checks;
3. terminal, unknown-event, malformed-line, cancellation, and redaction checks;
4. a no-model sandbox/process-control sentinel where the local CLI permits it;
5. fingerprint binding over Provider version, executable, help, platform,
   Adapter version, and policy version.

A changed fingerprint is reported as `stale`; an old report never silently
satisfies policy. Offline certification does not read credential contents.

Live certification requires an explicit command, cost acknowledgement, and
positive budget:

```powershell
muxdev provider certify codex --live --yes --max-cost-usd 0.10
```

It uses a disposable working directory and bounded timeout. Reports retain only
test id/hash, summary, exit state, and usage. A live report expires after 30
days and becomes stale immediately when a bound fingerprint changes. Default CI
uses Mock/Fake flows and never spends real Provider budget.

## Risk And Isolation Policy

RunSpec schema v2 persists `HarnessPolicySpec`:

```text
risk_level
risk_tags
required_capabilities
isolation_requirement
minimum_certification
```

`strict` gate or auth, payment, permission, secret, migration, or security tags
produce a high-risk task. Ordinary Codex/Qwen work requires current offline
certification, structured events, and verified Provider sandboxing. High-risk
real-Provider work requires current live certification, Provider sandboxing,
and cooperative cancellation. Managed Mock/Replay can satisfy deterministic
test/demo policy without pretending to be production delivery.

When high-risk requirements are not met, muxdev performs no Provider call. It
creates an `isolation_downgrade` Approval whose subject binds:

- Run and risk policy;
- Provider and Adapter versions;
- certification id, status, and fingerprint;
- verified and missing capabilities;
- expected and actual isolation;
- the next Provider Attempt generation.

Approval records a waiver; denial blocks the Run. A changed Provider,
fingerprint, policy, capability gap, isolation, or next Attempt produces a new
subject hash, so the old waiver is not reusable.

## Process, Credential, And Container Boundary

Provider processes receive an explicit environment allowlist containing OS
process essentials, locale, certificate/proxy settings, and approved private
state variables. Daemon environment secrets are not copied wholesale. Codex
copies only `auth.json` into daemon-private Provider state with owner-only
permission where supported; it does not copy `config.toml`, extensions, or MCP
configuration into the Attempt.

Subprocesses start in a distinct process group. Cancellation sends
SIGINT/CTRL_BREAK, waits the configured grace interval, then terminates the
exact controlled tree. Restart code never kills an unverified historic PID.

Docker execution adds a read-only root filesystem, isolated temporary mount,
all-capability drop, `no-new-privileges`, PID/CPU/memory limits, and network-off
default. Network is a separate option; container presence alone is not treated
as network isolation. These flags follow the [Docker run security controls](https://docs.docker.com/reference/cli/docker/container/run/).

## Four Fact Boundaries

| Record | Responsibility |
| --- | --- |
| Run State Event | business lifecycle: Run, Stage, Approval, ProviderAction |
| Execution Event | queue, lease, retry, cancellation, recovery |
| Harness Event | structured facts inside one Provider Attempt |
| Evidence | claims and verification material for delivered output |

Harness Events are strictly sequenced per Attempt with idempotency keys and a
SHA-256 chain. Payloads are redacted before persistence and label their source
as `provider`, `harness`, or `derived`. Critical events and Provider Attempt
projection commit in one transaction; WebSocket `harness_event@1` broadcasts
only after commit. Message deltas remain in bounded transcript files rather
than the database.

## Management Surface And Demo

```text
muxdev provider certify NAME [--offline|--live] [--yes] [--max-cost-usd N] [--json]
muxdev provider certification [NAME] [--json]
muxdev task harness-events RUN_ID [--stage ID] [--json]
muxdev task isolation RUN_ID [--json]
```

HTTP exposes only read operations for certifications, Harness Events, and
isolation. It has no live-certification, arbitrary command, image, SQL, or
Fixture-path route.

Demo sequence:

1. Show Codex/Qwen installed but uncertified.
2. Run offline certification and inspect verified versus advertised evidence.
3. Run Mock/Replay and inspect deterministic, hash-chained Harness Events.
4. Run an ordinary certified Codex/Qwen task and inspect actual isolation.
5. Submit a high-risk task without live certification and show the pre-launch
   `isolation_downgrade` Approval.
6. Change the Adapter fingerprint to demonstrate waiver invalidation.
7. Cancel an Attempt and inspect the cancellation and Attempt summary.

## Verification

The Week 4 suite covers provider-specific decoding, malformed/unknown events,
certification invalidation, no-model offline behavior, live acknowledgement,
trust separation, environment filtering, Replay containment, transaction
rollback, post-commit broadcast, high-risk approval gating, waiver staleness,
Docker hardening, and HTTP negative routes. On the current development machine,
Codex 0.144.1 and Qwen 0.18.4 pass offline certification.
