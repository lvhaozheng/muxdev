# muxdev v0.2 Trusted Agent Harness Plan

Status: **target architecture**. Unless a capability is explicitly listed as
current below, this document describes work planned for v0.2 rather than the
behavior of the v0.1 runtime.

Status labels used throughout: **当前已实现 (Current v0.1)** and
**v0.2 目标 (Target)**.

## Product Contract

muxdev is a local-first trusted delivery and routing control plane for coding
agents. It selects an eligible agent for a task, executes that task in an
isolated and recoverable unit, and produces evidence that explains what ran,
why it was selected, what changed, and whether the result is safe to deliver.

The primary audience is an individual developer using real repositories and
multiple coding-agent products. The initial production boundary is one machine
and one operator. Team self-hosting is a future deployment mode enabled by
replaceable queue, lease, artifact, and identity ports; multi-tenancy and remote
workers are not v0.2 commitments.

## Current Baseline

The v0.1 codebase already has useful foundations:

- local daemon, CLI, TUI, HTTP API, and dashboards;
- provider discovery plus Codex, Qwen, and deterministic mock CLI adapters;
- workflow stages, Git worktrees, approvals, rollback snapshots, reports, and
  hash-chained Evidence v2 records;
- project-scoped run artifacts and explicit memory promotion.

The baseline also has material gaps that v0.2 must not hide:

- the daemon queue is in-memory and thread-owned, without leases or restart
  reconciliation;
- generic CLI adapters observe output after execution and cannot reliably
  enforce action-level policy inside an opaque provider harness;
- SQLite durability, schema migration, API authorization, workspace boundaries,
  and cancellation are not yet production-grade;
- routing and learning signals are heuristic and do not establish that the
  selected agent is optimal for a task;
- LangGraph, generic plugins, semantic merge, parallel conflict hints, and
  multi-repository planning are not deep, stable main-path capabilities.

## Task Unit And Agent Team Model

The unit of orchestration is a task, not an agent conversation or fixed role
pipeline.

- Every task owns one isolated workspace, one durable state machine, and one
  main agent attempt at a time.
- The deterministic harness owns task state, policy, recovery, evidence, and
  human decisions. The agent remains autonomous inside those boundaries.
- A different certified agent may be added as a blind, read-only reviewer when
  the task risk policy requires it.
- Planning, coding, testing, and review are capabilities or task activities,
  not a mandatory sequence of independently chatting agents.

The target task states are `queued`, `routing`, `running`,
`waiting_approval`, `reviewing`, `verifying`, and the terminal states
`succeeded`, `failed`, and `cancelled`. Every transition will be represented by
an ordered, replayable event and guarded by an idempotency key.

## Target Public Contracts

### AgentHarnessAdapter

An adapter reports verified capabilities instead of inheriting them from a
provider name. Its stable responsibilities are:

- `probe`: return version, availability, trust tier, and certified capabilities;
- `start`, `resume`, and `cancel`: manage an attempt lifecycle;
- `events`: emit normalized messages, tool lifecycle, approval, diff, usage,
  artifact, and terminal events;
- declare whether native pause, resume, structured events, usage, and sandbox
  integration are actually supported.

Adapters have two trust tiers:

- `managed`: muxdev can observe structured actions and can pause or cancel at a
  defined protocol boundary;
- `opaque`: muxdev controls the process and workspace only and must not claim
  action-level interception.

Codex and Qwen are the first real certification targets. The mock and replay
adapters keep tests and product demonstrations deterministic.

### RouteDecision

Routing is quality- and risk-first:

1. Extract task type, language, repository size, change scope, risk tags, and
   required harness capabilities.
2. Exclude unavailable, uncertified, capability-ineligible, over-budget, or
   policy-incompatible agents.
3. Rank remaining agents using conservative quality confidence derived from an
   offline benchmark and evidence-verified outcomes.
4. Use safety, then cost and latency, as lower-order decisions.
5. Add a heterogeneous reviewer for high-risk tasks; block or record a human
   waiver when no eligible reviewer exists.

The immutable decision records task features, candidates, exclusions, scores,
policy version, and the selected main and review agents. Online outcomes update
routing history only when required evidence is complete.

### DeliveryAttestation

The implemented Week 6 attestation binds the task, route, adapter and policy versions,
starting and ending commits, patch, command exit codes, test outputs, approvals,
environment fingerprint, artifacts, and event-chain head. It will be signed by
a per-project local Ed25519 key and is verifiable offline through a bounded,
privacy-minimal `.muxattest` bundle. An unpinned bundle identity is explicitly
`self_asserted`; a matching out-of-band fingerprint is required for `trusted`.

## Stable, Experimental, And Removed Surface

Stable v0.2 product surface:

- task submission, inspection, cancellation, resume, rollback, and verification;
- project registration and isolated workspaces;
- harness adapter certification and normalized events;
- risk-constrained routing and optional heterogeneous review;
- policy-bound approvals and verifiable delivery evidence;
- CLI, API, and task-first dashboard views of the same state.

Experimental until benchmarked and connected to the main path:

- parallel write execution;
- advanced memory-based routing signals;
- multi-repository coordination;
- automatic CI rescue and cache optimization.

Removed from the stable claim or replaced:

- runtime `profile/topology` selection;
- LangGraph-first claims when the graph does not own execution and persistence;
- regex-based “semantic merge” as a semantic capability;
- provider score aggregation described as intelligent learning;
- generic plugin and capability skeletons that are not invoked by the runtime.

Legacy task commands may remain temporarily as aliases, but the target stable
CLI is `run`, `tasks`, `inspect`, `approve`, `resume`, `cancel`, `rollback`,
`verify`, `benchmark`, and `doctor`.

## Eight-Week Delivery Sequence

1. **Baseline truth:** document contracts, fix the existing test baseline,
   close workspace-boundary defects, and separate fast and integration CI.
2. **State and storage (implemented repository increment):** explicit reducer,
   ordered core lifecycle events, SQLite WAL, checksummed migrations,
   transactions, replay, and verified backup/restore.
3. **Durable runtime (implemented repository increment):** persistent RunSpecs
   and execution Jobs, a bounded Worker Pool, fenced leases, heartbeats,
   idempotency, cooperative cancellation, restart recovery, and explicit
   reconciliation for uncertain opaque Provider effects.
4. **Adapters and isolation (implemented repository increment):** certification
   contracts for Codex, Qwen, Mock, and Replay with visible trust/isolation.
5. **Routing (implemented repository increment):** bounded feature extraction,
   conservative evidence-backed routing, heterogeneous read-only review,
   immutable explanations, and side-effect-free replay. Benchmark execution
   and measured public quality claims remain release work.
6. **Trust (implemented repository increment):** typed Approval subjects,
   per-project Ed25519 identity, atomic signed completion, physically separate
   credentials, safe `.muxattest` export, and offline verification.
7. **Product (implemented repository increment):** `TaskStory v1`, one no-build
   task-first Dashboard, bounded authenticated timelines, and a registered
   four-minute Replay/managed-live simulation scenario.
8. **Release candidate (implemented repository increment):** executable
   Benchmark v2 with Blackboard v7 coordination, deterministic Replay,
   explicit budgeted live execution, random local API authentication, and
   reproducible `0.2.0rc1` build metadata. The real Provider Benchmark gate and
   all external publishing remain explicit operator actions.

## Benchmark And Demo

`trusted-routing-bench` will contain at least 24 held-out tasks across six task
classes and multiple repositories. Codex and Qwen both execute the tasks;
hidden tests, static checks, blind review blockers, and safety violations form
the quality outcome. Fixed-Codex, fixed-Qwen, legacy rules, and the v0.2 router
are compared using verified success, quality-adjusted regret, unsafe routing,
cost, latency, intervention, recovery, and evidence completeness.

The release criterion is zero high-risk capability mismatch and no more than
15% quality-adjusted regret versus the per-task oracle on held-out repositories.
Claims in the README and resume must use measured results and confidence
intervals, never pre-written improvement percentages.

The four-minute product demo uses held-out tasks, explains why Codex or Qwen was
selected, adds a heterogeneous reviewer for a sensitive change, injects one
daemon crash, verifies the final evidence, demonstrates tamper detection, and
compares the router with fixed-provider baselines. A deterministic replay mode
is required for interviews without network or provider credentials.

## v0.2 Acceptance Summary

- every state-boundary crash resumes without duplicate external effects;
- unregistered and escaping workspaces are rejected;
- unsupported adapter capabilities are visible and never silently simulated;
- a modified event, patch, test result, or approval subject fails verification;
- the fast PR suite completes within 60 seconds and the full suite is green on
  supported Windows, Linux, and macOS/Python combinations;
- documentation labels current behavior and target behavior separately.
